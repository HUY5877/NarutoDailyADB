# 雷电启动命令在 Windows 超时后仍阻塞

日期：2026-10-25；基线：远端 main `a68bda3`。本轮仅修复命令输出采集，不改变渠道选择、授权绑定或实例归属规则。

## 现场证据

- 正式任务 `bf0ee317-4994-4795-a300-afdcfe9dca25` 于北京时间 01:37:21 进入 `starting_emulator`，之后约每 21 秒出现实例池容量检查异常。
- 任务实际运行于本机 `NarutoDailyADB`，代码仍为 `b81bc27`。远端抓号功能 MR #23 已于 01:32:40 合并为 `a68bda3`，本机尚未拉取。因此该进程本身没有辅助应用检测分支。
- 只读检查本次绑定的实例 0：运行中、ADB `emulator-5554` 在线、`sys.boot_completed=1`、分辨率 `1920x1080`，两款应用 `com.huy.authcapture` / `com.tencent.tim` 均已安装，前台为安卓桌面。
- 本次绑定仍为 `reserved`、`serial=null`。Python 3.12.8 子进程栈停在 `start()` 的 ADB serial 查询，经 `_run_result()` 进入 `subprocess.run()` 超时后的第二次 `communicate()`，等待输出读取线程结束。

Windows 的 `subprocess.run(..., stdout=PIPE, stderr=PIPE, timeout=...)` 在命令超时并终止直接子进程后，会无超时限制地再次收集输出。如果子孙进程继承输出管道并保持存活，读取线程仍可能无限等待。现场栈确认该等待点；独立 Python 子孙进程测试复现此行为，不需要操作共享 ADB server。

`start()` 在启动和就绪检查期间持有实例状态锁；另一个消费者等待该锁 20 秒失败，暂停 1 秒后再试，产生重复警告。该告警不是“找不到抓号器”，正常实例全忙时也不会输出它。

## 修复和范围

命令标准输出、错误输出改用自动清理的临时文件，仍由 `subprocess.run` 等待直接命令并执行超时处理。命令退出后读取有限长度的输出快照并返回原来的 `CompletedProcess` 字节输出；保留返回码白名单、长操作期限以及脱敏异常。

不终止共享 ADB server，不杀无关进程，不清空应用或实例数据。Windows 超时修复与本机拉取新版本是两件事；修复文件不会改变已运行进程。

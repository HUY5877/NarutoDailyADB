# 明文授权与手动 token 登录

用户要求在数据库中直接复制 QQ token，并粘贴到上号器使用。工作限定在两个仓库的 test 分支。

## 方案

数据库保存明文 access_token、openid、callback_url；已有密文使用原密钥在事务中迁移，保留编号、归属、备注、捕获时间及真实有效期。新上传不再加密。原密钥仅用于迁移旧记录，迁移失败整体回滚。

上号器提供 token 输入框和“使用 token”按钮。客户端通过当前网站账号的 Cookie 调用 POST /api/qq-authorizations/resolve，正文为 {"access_token":"原始token"}；接口仅匹配本人记录，返回现有 {item,authorization}，保留完整回调中的扩展参数及原始到期时间。客户端校验结果后选择对应记录，后续游戏登录沿用当前按编号下载并确认的流程。选择账号列表仍可用。

仅靠原始 token 离线伪造 openid、有效期或完整回调不可靠，因此继续从已有授权记录读取配套字段。保留数据库密文加一个复制按钮不满足用户明文存储的明确要求。

## 约束与验收

- 用户只需粘贴十六进制 token，允许首尾空白，不改变 token 大小写；不得把 token 放进 URL、日志或错误文本。
- 所有 API 仍要求网站登录、限制记录所属用户，并保留 test 环境与实际数据库名双重检查。
- 空值、非法 token、别人的 token、过期记录、重复匹配、切换网站账号后的迟到响应均不能选中错误账号。
- 数据库迁移须处理过期旧记录而不延长有效期，错误密钥和损坏记录不得造成部分迁移。
- 构建并验证 APK；若缺少原签名，先保留可审查构建结果，不能未经用户同意卸载现有应用造成数据丢失。
- 所有提交中文；不修改或推送 main。

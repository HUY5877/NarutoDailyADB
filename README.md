# NarutoDailyADB

雷电模拟器 9 的 ADB 坐标自动化实验项目。

第一阶段目标是以固定安卓分辨率和显式坐标配置，分别调试登录、组织祈福、两次免费招财、签到、领取体力、免费招募和一次丰饶之间战斗。项目不包含内存读取、注入、改包、验证码处理、付费操作或反检测功能。

> 在线游戏自动化可能违反游戏服务规则并带来账号风险。请仅在理解风险的前提下用于个人研究和界面自动化测试。

## 目录结构

代码按功能放在 `naruto_daily/` 的子目录中，总体流程保留在根目录：

```text
naruto_daily/
├── cli.py                   # 命令行入口
├── config.py                # 配置读取与校验
├── tasks.py                 # 任务顺序与组合
├── runner.py                # 总体动作调度
├── common/                  # ADB、图像识别、卡片查找、共用结果类型
├── multimodal/              # client.py：模型调用；prompts.py：提示词模板
├── login/                   # 账号控件、昵称确认、授权、登录弹窗
├── fortune/                 # 金币招财
├── organization_prayer/     # 组织祈福与昨日奖励
├── abundance/               # 丰饶之间入口与结算
├── battle/                  # 通用战斗循环
├── return_to_main/          # 关闭页面并确认返回主界面
└── recruit/                 # 免费招募
```

各功能包的 `__init__.py` 导出任务入口，实现放在包内；跨功能共用能力集中在 `common/`。图片仍放在项目的 `assets/`，配置和密钥文件位置不变，原有命令行用法不变。

## 安装

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
Copy-Item config.example.json config.local.json
```

先打开雷电模拟器，再检查 ADB 和安卓分辨率：

```powershell
.\.venv\Scripts\naruto-daily.exe check --config config.local.json
```

## 校准和运行

示例配置已按当前雷电 `1920×1080` 安卓画面填写登录、组织祈福、两次免费招财、免费忍者招募和丰饶之间流程；签到和体力任务仍为空。登录坐标来自实际页面：勾选协议、安卓 QQ、授权同意、开始游戏、关闭公告。

关闭公告并领取当天登录奖励后，脚本会调用通用“回到主界面”流程。每轮先识别主界面的“奖励”文字（`assets/main_reward_label.png`，避开红点），确认已经处于主界面时立即结束，不再检查右上角叉。仅在尚未回到主界面时，才以 `0.95` 的阈值识别透明背景的橙红色叉；识别成功后先等待 1 秒，再次检查主界面和关闭按钮，确认仍需关闭才点击，点击后再等待 1 秒。该流程最多检查十轮，可以逐层关闭新忍者、新活动以及二级、三级界面。只有明确识别到“奖励”入口才算成功返回主界面；连续两轮既没有主界面标记也没有关闭叉时会报错停止，不会把未知页面当成主界面。

现场截图中，活动页真实关闭叉的离线相似度约为 `0.997`，主界面“活动”图标对关闭模板的误匹配分数约为 `0.837`。误匹配较高是因为关闭模板仅保留橙红色叉的非透明像素，而遮罩模板使用的归一化相关算法偏重颜色和亮度方向；“活动”图标也包含大量橙红色高亮和深色边缘。现在通过主界面优先识别和 `0.95` 关闭阈值共同阻断该误点。

请只从第一张登录页面开始运行；如果已经处于后续页面，不要执行完整登录流程。

登录阶段先勾选协议，再识别安卓 QQ 按钮进入授权页。按钮点击前重新截图确认；超时则停止流程并输出中文错误。

第一次授权固定使用“离落花开花败”。`authorize_account` 将授权截图交给多模态模型提取当前昵称，在本地做完整字符串匹配。昵称不一致时打开“切换账号”，通过安卓控件文字精确找到目标账号并点击，等待 3 秒后再次用模型核对昵称。点击同意前重新截图读取昵称；未知昵称、接口异常、超过时间或调用上限时停止，不使用昵称图片兜底。按钮与弹层标题仍用图片识别。

`naruto_daily/multimodal/client.py` 是通用的图片 + 提示词 → JSON API 客户端，包含超时、响应校验和异常脱敏；`naruto_daily/multimodal/prompts.py` 单独保存场景提示词，后续多模态场景可复用客户端并添加模板。提示词不预填目标账号，模型只负责读取，是否匹配由本地代码决定。

示例和本机配置的 `multimodal` 使用 `https://api.stepfun.com/step_plan/v1`、`step-3.7-flash`。该模型支持图片输入，接口方式见 [Step Plan 官方文档](https://platform.stepfun.com/docs/zh/step-plan/integrations/reasoning-api)。密钥由 `api_key_file` 指向配置目录下的 `.secrets/stepfun_api_key`；该目录已加入 Git 忽略，新机器需自行创建密钥文件。授权截图会发送至配置的模型服务。默认单次请求上限 20 秒，每次授权最多 6 次调用；网络耗时计入 40 秒阶段预算。昵称未能读取时仍使用统一的等待 1 秒重新截图补查逻辑。

第一次授权完成后，脚本会同时等待“第二次授权页面”或“开始游戏按钮”。如果直接出现开始游戏，说明本次只需一次授权；如果出现第二次授权页面，则点击第二次同意后继续等待开始游戏。该分支最多等待 40 秒。

登录链路中的图片按钮首次识别成功后会先等待 3 秒，再次确认按钮仍存在后才点击，点击完成后再等待 3 秒让页面响应。按钮在前置等待期间消失时不会点击旧坐标，而是继续识别。等待时长可通过 `pre_click_wait_seconds` 和 `post_click_wait_seconds` 调整。登录授权和进入游戏的加载等待保持原值；进入游戏后的弹窗清理、返回主界面、祈福、招财和招募，其点击前后、轮询及滑动后的等待均设为 1 秒。识别超时上限保持原值。

所有游戏图片判断统一通过 `naruto_daily/common/recognition.py`：首次未确认目标时，等待 1 秒并重新截图补查一次；首次成功不增加等待，补查仍失败则继续原来的超时、滑动、跳过或报错规则。点击前复查也使用这套逻辑。任务卡片每次重新定位文字和按钮；主界面与关闭按钮、登录分支、招募红点与目标按钮按同一帧判断，避免使用旧坐标或混用不同画面。原有超时流程会计入补查等待；距离超时不足 1 秒时不再追加补查，优先遵守原超时上限。招财仍按连续三轮未确认结束，每轮包含首次检查和一次补查。日志会显示“1.00 秒后重新截图补查一次”及补查结果。

各流程每轮开始会输出 `[场景 第N轮]`，简要说明本轮检查顺序、点击条件、退出条件，以及适用的轮数上限、剩余等待或模型调用次数。未完成时会说明下一轮前的等待和后续动作。图片“补查”是当前轮次内额外截图一次，不等于开始下一轮；补查失败会明确显示“返回当前轮次判断（未点击）”。账号授权、登录、找卡片、清弹窗、回主界面、招募、招财、祈福领奖、丰饶挑战及战斗检查都采用这一日志格式。

组织祈福任务会先等待并点击主界面右侧的“奖励”，然后逐屏向右滑动任务栏并识别“组织祈福”文字。找到后只检查该卡片自身下半部分：出现“已完成”就记录日志并结束本次任务；出现“立刻前往”才点击实际识别到的按钮中心。两者都没有时会报错停止。任务卡片位置不固定，最多横向滑动六次；脚本不会使用全局固定按钮坐标，也不会点击相邻的“冒险副本挑战”“忍者招募”等卡片。

进入组织祈福页面后，脚本先等待“6000 铜币焚香祈福”出现，以确认页面加载完成。左上角出现“昨日奖励”时会打开其奖励界面，等待识别到“昨日祈福奖励”标题后，每次重新截图并只点击一个橙色“领取”；“未达成”不会被点击。奖励处理完后点击右上安全空白处关闭界面，再重新识别并点击“6000 铜币焚香祈福”。昨日奖励不存在时直接跳过领取。奖励固定为三档，因此最多领取三次；三档全部领取属于正常完成。

祈福处理结束后，脚本用通用回主界面流程逐层点击右上角叉，再次进入“奖励”并横向查找“进行1次金币招财”。卡片显示“已完成”时只跳过招财；否则只点击该卡片下方对应的“立刻前往”。进入招财页后，脚本仅在底部中间安全区域识别 `assets/free_fortune_once.png`，按“识别、等待 1 秒、再次确认、点击、等待 1 秒”的顺序完成两次免费招财。右侧付费按钮位于搜索区域之外，也不使用它的模板。

两次免费招财结束后，脚本再次回到主界面、打开“奖励”，横向查找未完成的“忍者招募”卡片并点击该卡片下方的“立刻前往”。进入招募页后，高级招募和普通招募共用透明背景的 `assets/recruit_red_dot.png`，但分别只在各自标签右上角的小区域检测，阈值固定不低于 `0.95`。对应位置没有红点就跳过；发现红点后先等待 1 秒并二次确认，确认仍存在才选择该标签，选择后还会再次检查红点，再只在底部中间安全区域识别包含“免费”字样的按钮。免费按钮首次出现后等待 1 秒并再次确认，结果页只在左下安全区域识别并点击“确定”，右侧“招募1次”“招募10次”等付费选项全部位于检测区域之外。普通招募无论显示免费几抽，都按一次免费操作处理。

免费招募后继续执行丰饶之间：回主界面、打开奖励、识别“挑战丰饶之间”卡片并点击对应的“立刻前往”。卡片已完成时跳过挑战和战斗，仍执行最后的回主界面动作。进入挑战页后只识别左侧“挑战”按钮，点击后固定等待 10 秒，再等待战斗暂停按钮出现，确认进入战斗。

通用战斗代码在 `naruto_daily/battle/handler.py`，按配置的“一技能 → 二技能 → 大招 → 普攻”顺序循环。每次点击前使用统一图片识别判断当前画面；未确认战斗画面时暂停输入，结算标记优先于战斗标记。战斗点击间隔独立设为 0.2 秒（另有 ADB 截图和输入耗时），普通界面等待仍为 1 秒。丰饶之间使用“丰饶之间获得奖励”标题确认战斗结束，再识别并点击底部“点击任意位置关闭界面”，最后调用通用回主界面功能。

战斗配置位于 `tasks.abundance` 的 `handle_abundance.battle`，可调整四个按钮坐标、点击间隔、战斗画面标记及结束标记。当前战斗上限为 120 秒，并计入 ADB 操作耗时；超时会停止，不会把黑屏或未知页面当成胜利。任务和组合流程不限制动作总数，也不检查累计等待预算。`run abundance` 可单独运行该任务。

坐标必须是安卓内部坐标，不能使用包含雷电标题栏和右侧工具栏的桌面坐标。

先打印动作而不发送输入：

```powershell
.\.venv\Scripts\naruto-daily.exe run sign_in --config config.local.json --dry-run
```

登录主流程先 dry-run，再从第一张登录页面实际执行。该命令会在清理登录弹窗后继续执行组织祈福、两次免费招财、免费忍者招募和丰饶之间：

```powershell
.\.venv\Scripts\naruto-daily.exe run login --config config.local.json --dry-run
.\.venv\Scripts\naruto-daily.exe run login --config config.local.json
```

逐项测试：

```powershell
.\.venv\Scripts\naruto-daily.exe run organization_pray --config config.local.json
.\.venv\Scripts\naruto-daily.exe run sign_in --config config.local.json
.\.venv\Scripts\naruto-daily.exe run stamina --config config.local.json
.\.venv\Scripts\naruto-daily.exe run recruit --config config.local.json
.\.venv\Scripts\naruto-daily.exe run abundance --config config.local.json
```

全部坐标分别验证后，才运行 `all`。该命令开始前有五秒倒计时，可按 Ctrl+C 取消：

```powershell
.\.venv\Scripts\naruto-daily.exe run all --config config.local.json
```

脚本仍以固定分辨率和固定安全区域为基础，只在关键页面使用模板识别。任何页面大幅改版、中断或加载异常都会停止当前流程；不要把付费、金币购买或付费确认按钮加入配置。

脚本运行时会在终端打印中文日志，包括动作序号、点击坐标、等待时间、模板相似度、是否发现领取按钮以及错误原因。

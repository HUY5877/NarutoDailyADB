# NarutoDailyADB

所有大模型 HTTP 请求共用 `naruto_daily/multimodal/transport.py`：普通 JSON 图片识别、OpenAI 兼容导航和 Claude 导航均在网络异常、HTTP 408/429/500/502/503/504 时最多重试 **3 次**，每次间隔 **2 秒**，连同首次请求最多 **4 次**。401/403 等不可重试错误立即停止；等待和请求均计入已有阶段时限。SDK 自带请求重试已关闭，接口重试耗尽后也不会被外层识别流程再次重试。重试只重发当前模型请求，不重跑游戏点击或移动。

## 扫码登录 worker（Python）

新增的 [login_service](naruto_daily/login_service/README.md) 使用 Python 实现，与现有日常自动化独立运行。配置 `REDIS_URL` 后，它作为常驻 worker 从真实 Redis 队列消费登录任务，每个任务启动独立 Python 子进程模拟雷电及游戏登录步骤，生成二维码后写入 OSS，并回写 Redis 会话状态。当前二维码仅用于联调，不能授权真实账号；真实雷电与游戏点击尚未实现。

客户端前后端位于 [NarutoLoginClient](https://github.com/HUY5877/NarutoLoginClient)，仍使用 TSX + TypeScript。网站/Vercel 后端投递 Redis 任务、查询状态并读取 OSS；Python worker 不开放 HTTP 端口，网站无需连接本机 Python。两边必须使用相同的 Redis 数据库、队列和 OSS 配置；默认队列为 `naruto:login:tasks`，OSS 前缀为 `login`。

在本项目根目录执行 `python -m pip install -e ".[login-service]"`，在服务专用 `naruto_daily/login_service/.env` 中设置 `REDIS_URL` 并保留已有 OSS 配置，再执行 `python -m naruto_daily.login_service`。本机可直接运行 `.\.venv-login-service\Scripts\python.exe -m naruto_daily.login_service`。进程会持续消费任务，断线自动重连，按 `Ctrl+C` 优雅停止；强制终止后已取出的任务可能需要重新申请。`REDIS_URL` 为必填项，未配置或为空时会明确报错并以退出码 1 结束，不启动本地 Web 服务，详见模块文档。

## 双击启动（Windows）

完成下方安装和配置后，先打开模拟器并停留在**第一张登录页面**，然后双击项目根目录里的脚本：

| 脚本 | 执行流程 |
| --- | --- |
| [启动日常.cmd](启动日常.cmd) | 日常完整队列（`all`）：登录、一乐外卖、装备养成、祈福及招财、免费招募、签到、体力、丰饶、生存挑战、奖励入口秘境；未配置的任务跳过。 |
| [启动秘境.cmd](启动秘境.cmd) | 独立刷秘境（`secret_realm_farm`）：登录后从“忍者挑战”进入“秘境探险”，按挑战券循环。 |

脚本自动使用项目的 `.venv` 和 `config.local.json`，无需手动激活环境或输入启动命令。启动后由独立的 Python 窗口显示日志，批处理启动窗口自动退出。运行中按 `Ctrl+C` 直接停止并关闭运行窗口，不再询问 `Terminate batch job (Y/N)?`；正常结束或出错后保留日志，按回车关闭。两条线路均包含登录动作，请每次只运行一个脚本。

需要预览动作时，也可在 PowerShell 中运行 `.\启动日常.cmd --dry-run` 或 `.\启动秘境.cmd --dry-run`；预览会检查设备连接和分辨率，但不点击、不调用模型。

## 目录结构

代码按功能放在 `naruto_daily/` 的子目录中，总体流程保留在根目录：

```text
naruto_daily/
├── cli.py                   # 命令行入口
├── launcher.py              # 双击启动的日志窗口和 Ctrl+C 退出处理
├── config.py                # 配置读取与校验
├── tasks.py                 # 任务顺序与组合
├── runner.py                # 总体动作调度
├── common/                  # ADB、图像识别、卡片查找、共用结果类型
├── multimodal/              # client.py：模型调用；prompts.py：提示词模板；agent/：通用视觉导航
├── login/                   # 账号控件、昵称确认、授权、登录弹窗
├── ichiraku.py              # 一乐外卖可领取判断及领取
├── equipment/              # 最低进阶装备的材料扫荡、合成、装备和进阶
├── fortune/                 # 金币招财
├── organization_prayer/     # 组织祈福与昨日奖励
├── abundance/               # 丰饶之间入口与结算
├── secret_realm/            # 秘境房间、挑战券读取和循环出战
├── battle/                  # 通用战斗循环
├── return_to_main/          # 关闭页面并确认返回主界面
└── recruit/                 # 免费招募
```

各功能包的 `__init__.py` 导出任务入口，实现放在包内；跨功能共用能力集中在 `common/`。图片仍放在项目的 `assets/`，流程参数保留在 JSON，接口和账号配置集中在同目录的 `.env`，命令行用法不变。

## 校准和运行

示例配置已按当前雷电 `1920×1080` 安卓画面填写登录、组织祈福、两次免费招财、免费忍者招募、丰饶之间和生存挑战流程；签到和体力任务仍为空。登录坐标来自实际页面：勾选协议、安卓 QQ、授权同意、开始游戏、关闭公告。

关闭公告并领取当天登录奖励后，脚本会调用通用“回到主界面”流程。每轮先识别主界面的“奖励”文字（`assets/main_reward_label.png`，避开红点），确认已经处于主界面时立即结束，不再检查右上角叉。仅在尚未回到主界面时，才以 `0.95` 的阈值识别透明背景的橙红色叉；识别成功后先等待 1 秒，再次检查主界面和关闭按钮，确认仍需关闭才点击，点击后再等待 1 秒。该流程最多检查十轮，可以逐层关闭新忍者、新活动以及二级、三级界面。“奖励”文字同时支持原模板和带红点截图对应的备用文字模板（`alternate_templates`），两种模板在同一张截图、同一搜索区域内匹配，阈值保持0.90。日志打印主界面标记的匹配分数、阈值、区域和模板数量。只有明确识别到“奖励”入口才算成功返回主界面；连续两轮既没有主界面标记也没有关闭叉时会报错停止，不会把未知页面当成主界面。

现场截图中，活动页真实关闭叉的离线相似度约为 `0.997`，主界面“活动”图标对关闭模板的误匹配分数约为 `0.837`。误匹配较高是因为关闭模板仅保留橙红色叉的非透明像素，而遮罩模板使用的归一化相关算法偏重颜色和亮度方向；“活动”图标也包含大量橙红色高亮和深色边缘。现在通过主界面优先识别和 `0.95` 关闭阈值共同阻断该误点。

请只从第一张登录页面开始运行；如果已经处于后续页面，不要执行完整登录流程。

登录阶段先勾选协议，再识别安卓 QQ 按钮进入授权页。按钮点击前重新截图确认；超时则停止流程并输出中文错误。

第一次授权使用 `.env` 中 `LOGIN_ACCOUNT_NAME` 指定的昵称。`authorize_account` 将授权截图交给多模态模型提取当前昵称，在本地做完整字符串匹配。昵称不一致时打开“切换账号”，通过安卓控件文字精确找到目标账号并点击，等待 3 秒后再次用模型核对昵称。点击同意前重新截图读取昵称；未知昵称、接口异常、超过时间或调用上限时停止，不使用昵称图片兜底。按钮与弹层标题仍用图片识别。

`naruto_daily/multimodal/client.py` 是通用的图片 + 提示词 → JSON API 客户端，包含超时、响应校验和异常脱敏；`naruto_daily/multimodal/prompts.py` 单独保存场景提示词，后续多模态场景可复用客户端并添加模板。提示词不预填目标账号，模型只负责读取，是否匹配由本地代码决定。

通用导航位于 `naruto_daily/multimodal/agent/`，使用 Pydantic AI 的 `Agent` 管理会话和工具循环，移动工具负责截图和 ADB。`secret_realm/pre_battle.py` 在通用 `battle.run_battle()` 之前执行检查：阴阳秘境退出；毒风秘境由 `secret_realm/navigation.py` 传入目标和完成条件。agent 每一步在同一次工具调用中读取页面、提示文字和 BOSS/交战证据，再决定移动或结束；待解封提示明确消失且有 BOSS 或实际交战证据时，才进入战斗。不会在 agent 结束后再调用模型复核。最多移动 50 步，步数用尽仍未解封则退出；识别到失败/结算或页面不确定则停止。退出后回房间重新读券，不计为通关；无需额外传命令行参数。详见 [agent 使用说明](naruto_daily/multimodal/agent/README.md)。

默认使用 ModelLink 中国大陆接入点：`.env` 中设置 `MULTIMODAL_BASE_URL=https://api.qnaigc.com/v1`、`MULTIMODAL_MODEL=deepseek/deepseek-v4.1-flash`，并将 `MULTIMODAL_API_KEY` 替换为自己的 ModelLink 密钥。 OpenAI 兼容地址带 `/v1`，Anthropic 兼容地址使用同一域名但去掉 `/v1`；程序会根据 Base URL 自动选择对应客户端。接入点说明见 [ModelLink 文档](https://docs.modelink.ai/api-endpoints/overview#mainland-china-endpoint)。

JSON 中的 `account_name`、`multimodal.base_url` 和 `multimodal.model` 分别使用 `${LOGIN_ACCOUNT_NAME}`、`${MULTIMODAL_BASE_URL}` 和 `${MULTIMODAL_MODEL}` 引用环境配置。`naruto_daily/common/environment.py` 统一读取和解析环境变量，多模态客户端调用前单独读取 `MULTIMODAL_API_KEY`，密钥不会放进任务动作列表。旧的 `api_key_file` 配置已移除。授权截图会发送至配置的模型服务。默认单次请求上限 20 秒，每次授权最多 6 次调用；网络耗时计入 40 秒阶段预算。昵称未能读取时仍使用统一的等待 1 秒重新截图补查逻辑。

第一次授权完成后，脚本会同时等待“第二次授权页面”或“开始游戏按钮”。如果直接出现开始游戏，说明本次只需一次授权；如果出现第二次授权页面，则点击第二次同意后继续等待开始游戏。该分支最多等待 40 秒。

登录链路中的图片按钮首次识别成功后会先等待 3 秒，再次确认按钮仍存在后才点击，点击完成后再等待 3 秒让页面响应。按钮在前置等待期间消失时不会点击旧坐标，而是继续识别。等待时长可通过 `pre_click_wait_seconds` 和 `post_click_wait_seconds` 调整。登录授权和进入游戏的加载等待保持原值；进入游戏后的弹窗清理、返回主界面、祈福、招财和招募，其点击前后、轮询及滑动后的等待均设为 1 秒。识别超时上限保持原值。

所有游戏图片判断统一通过 `naruto_daily/common/recognition.py`：首次未确认目标时，等待 1 秒并重新截图补查一次；首次成功不增加等待，补查仍失败则继续原来的超时、滑动、跳过或报错规则。点击前复查也使用这套逻辑。任务卡片每次重新定位文字和按钮；主界面与关闭按钮、登录分支、招募红点与目标按钮按同一帧判断，避免使用旧坐标或混用不同画面。原有超时流程会计入补查等待；距离超时不足 1 秒时不再追加补查，优先遵守原超时上限。招财仍按连续三轮未确认结束，每轮包含首次检查和一次补查。日志会显示“1.00 秒后重新截图补查一次”及补查结果。

各流程每轮开始会输出 `[场景 第N轮]`，简要说明本轮检查顺序、点击条件、退出条件，以及适用的轮数上限、剩余等待或模型调用次数。未完成时会说明下一轮前的等待和后续动作。图片“补查”是当前轮次内额外截图一次，不等于开始下一轮；补查失败会明确显示“返回当前轮次判断（未点击）”。账号授权、登录、找卡片、清弹窗、回主界面、招募、招财、祈福领奖、丰饶挑战及战斗检查都采用这一日志格式。

登录关闭弹窗后首先执行 `ichiraku_takeout`：进入活动的一乐外卖，由模型识别三处外卖是否可领取，先点击最左侧仍可领取的盒子，复查后若还有可领盒子则依次领取剩余，每个位置最多点击一次；确认领取结果后调用通用回主界面。全部不可领取则直接返回；“售罄”“休息”和体力追回不作为可领取盒子。

随后执行 `equipment_upgrade`：点击主界面装备及二级菜单装备，模型读取六件装备图标中的 `+` 进阶数，选择最低的一件（不是相同的 `Lv` 数；同值按从左到右、从上到下）。再次读取所选装备的六个材料框，从左到右处理缺少的成品。完整彩色成品且无该格加号或待添加提示时视为已装备；若点击后打开的是仅含说明和属性的成品信息卡，关闭后重新确认同一装备的该格已装好，再处理后面的材料，确认不一致则停止。一键扫荡后、开始扫荡前读取当前体力和“材料足够后自动停止”的勾选状态。体力 **>5** 且明确未勾选时，点击该复选框一次，再重新截图确认已勾选后才开始扫荡；已勾选则直接继续，状态不明确或点击后复查仍未确认时停止，不反复切换复选框。复查后按最新体力判断是否大于5。扫荡后读取当次结果的实际完成次数、体力和动画状态，确认已显示最后一次奖励且完成动画结束；不再跨轮比较两次开始前体力。点击空白后重新确认前景已回到材料详情，不能仅凭“继续扫荡”消失判断结果层关闭（材料足够和动画遮挡都会让该按钮消失）；结果核验、关闭和识别重试共用扫荡时限；出现合成就合成，再装备，重新选择最低进阶装备。合成后若仍显示可用的合成按钮，等待1秒并重新截图补查；补查仍确认可合成才重试，最多点击合成3次，确认装备按钮后才装备，未知状态或超时则停止。成品齐全时点击右下“进阶”，再重新比较装备。体力≤5时收起弹层、回主界面并继续后续日常；未知页面或数值不按0处理。模型每个判断最多识别3次，单次接口请求超时30秒；单次扫荡最多等待120秒，装备任务最多100轮、3600秒。

这两个模块可分别运行：`.\.venv\Scripts\naruto-daily.exe run ichiraku_takeout --config config.local.json` 和 `.\.venv\Scripts\naruto-daily.exe run equipment_upgrade --config config.local.json`。`login`、`all` 已按上述顺序接入；独立刷秘境线路不包含这两个任务。截图使用原始1920×1080 ADB画面，模型选择编号由代码映射到装备、材料和外卖盒子的固定区域。

组织祈福任务会先等待并点击主界面右侧的“奖励”，然后逐屏向右滑动任务栏并识别“组织祈福”文字。找到后只检查该卡片自身下半部分：出现“已完成”就记录日志并结束本次任务；出现“立刻前往”才点击实际识别到的按钮中心。两者都没有时会报错停止。任务卡片位置不固定，最多横向滑动六次；脚本不会使用全局固定按钮坐标，也不会点击相邻的“冒险副本挑战”“忍者招募”等卡片。

进入组织祈福页面后，脚本先等待“6000 铜币焚香祈福”出现，以确认页面加载完成。左上角出现“昨日奖励”时会打开其奖励界面，等待识别到“昨日祈福奖励”标题后，每次重新截图并只点击一个橙色“领取”；“未达成”不会被点击。奖励处理完后点击右上安全空白处关闭界面，再重新识别并点击“6000 铜币焚香祈福”。昨日奖励不存在时直接跳过领取。奖励固定为三档，因此最多领取三次；三档全部领取属于正常完成。

祈福处理结束后，脚本用通用回主界面流程逐层点击右上角叉，再次进入“奖励”并横向查找“进行1次金币招财”。卡片显示“已完成”时只跳过招财；否则只点击该卡片下方对应的“立刻前往”。进入招财页后，脚本仅在底部中间安全区域识别 `assets/free_fortune_once.png`，按“识别、等待 1 秒、再次确认、点击、等待 1 秒”的顺序完成两次免费招财。右侧付费按钮位于搜索区域之外，也不使用它的模板。

两次免费招财结束后，脚本再次回到主界面、打开“奖励”，横向查找未完成的“忍者招募”卡片并点击“立刻前往”。招募按高级、普通顺序处理，标签和红点仍使用图片识别。切换标签后，通用多模态客户端读取当前选中标签、按钮完整文字和免费抽数，例如“免费”“免费1抽”“免费5抽”（只写“免费”时按单次处理）；倒计时、“后增加一次免费”和消耗招募券的按钮不能当作免费按钮。

免费按钮不再使用 OpenCV 模板，识别提示词是 `multimodal/prompts.py` 中的 `FREE_RECRUIT`，点击流程在 `recruit/free_button.py`。同一张截图中必须同时确认对应红点和免费按钮；等待 1 秒后重新截图再次调用模型，标签及免费抽数一致才点击配置中的 `free_button.click_x/click_y`，不使用模型估计坐标。当前点击位置为 `(1330, 865)`，位于已验证的高级、普通免费按钮内部；坐标必须在配置的按钮区域内。完成后关闭招募结果，每种招募最多执行一次按钮点击，不会按识别到的抽数重复点击。

招募的 `multimodal` 与登录使用同一套 `.env` 接口配置。每个招募类别的免费按钮识别最多调用模型 6 次，单次请求上限 30 秒，阶段上限 60 秒，网络推理时间计入阶段耗时。首次未确认仍等待 1 秒重新截图补查一次；接口异常、超时或无法确认时不点击。日志显示每轮动作、免费抽数、配置点击位置和模型调用次数。

免费招募后继续执行丰饶之间：回主界面、打开奖励、识别“挑战丰饶之间”卡片并点击对应的“立刻前往”。卡片已完成时跳过挑战和战斗，仍执行最后的回主界面动作。进入挑战页后只识别左侧“挑战”按钮，点击后固定等待 10 秒，再直接调用战斗模块开始技能循环。

丰饶之间完成后会执行生存挑战：从奖励卡片进入后，如果页面出现“传送”提示先点击任意位置关闭；随后点击“开始扫荡”。出现出战名单时点击“准备就绪”，再确认名单和扫荡；若名单已经确认过、直接出现扫荡券提示，则只确认扫荡。按钮使用原始 1920×1080 ADB 截图裁剪的模板，每一步最多等待 20 秒，截图和匹配耗时计入上限，日志显示相似度。扫荡确认后等待 60 秒，再由多模态模型读取页面底部的“重置次数”。读到 0 结束，读到大于 1 时点击“重置”和确认继续下一轮；无法确认或读到 1 会停止，避免误操作。完成后统一回到主界面，再进入秘境任务。

通用战斗代码在 `naruto_daily/battle/handler.py`，同时向一技能、二技能、大招、普攻四个按钮发送点击，不保证技能先后顺序。一批四个输入全部返回后立即开始下一批，不积压后台点击。进入战斗时检查一次结算，之后每隔20秒再截图检查一次，期间持续连点；检查周期按实际经过时间计算，包含 ADB 输入耗时，到期后等当前批次完成再检查。发现结束标记立即停止，结算出现后可能继续点击到下一次检查。`tap_interval_seconds` 控制两批点击之间的额外等待，默认0秒，实际速度取决于 ADB 和模拟器；普通界面等待仍为1秒。加载等待由调用方完成，战斗超时仍会停止点击。丰饶正常结算仍复查并点击底部“点击任意位置关闭界面”。配置了动作层 `multimodal` 时，战斗模板未命中会交给模型判断是否停止连点；收尾阶段若结算文字已消失，则复用同一个客户端重新识别当前页面。确认是超影服务弹窗或真正结算页时，都只点击一次已实机验证的左侧空白处 `(400, 540)`，等待后交给下一步通用回主界面功能检查关闭叉。已回到未被遮挡的丰饶页面或主界面时不再等待结算文字；未知页面、其他弹窗和识别异常均不盲点。战后页面识别最多调用一次，截图和请求耗时计入收尾超时。

战斗配置位于 `tasks.abundance` 的 `handle_abundance.battle`，可调整四个按钮坐标、点击间隔、战斗画面标记及结束标记。当前战斗上限为 120 秒，并计入 ADB 操作耗时；超时会停止，不会把黑屏或未知页面当成胜利。任务和组合流程不限制动作总数，也不检查累计等待预算。`run abundance` 可单独运行该任务。

坐标必须是安卓内部坐标，不能使用包含雷电标题栏和右侧工具栏的桌面坐标。

## 秘境探险

独立刷秘境线路运行方式（在项目目录执行）：

```powershell
.\.venv\Scripts\naruto-daily.exe run secret_realm_farm --config config.local.json
```

`secret_realm_farm` 顺序为：登录并处理授权、弹窗 → 回主界面 → 向左滑一次 → 大模型定位并点击“忍者挑战” → 大模型定位并点击最左侧“秘境探险” → 创建房间 → 读券、战斗、结算返回循环 → 券为0后回主界面。它不会执行组织祈福、招募、丰饶等每日任务，也不会因为奖励卡片已完成而跳过秘境。追加 `--dry-run` 可查看动作队列，不点击、不调用模型。

两种入口在 `naruto_daily/secret_realm/enter.py`：`enter_from_rewards` 使用奖励卡片，`enter_from_ninja_challenge` 使用主界面。配置中 `tasks.secret_realm_farm` 只放新入口；`tasks.py` 将它与原始登录动作、`tasks.secret_realm` 从 `handle_secret_realm` 起的公共后续动作组合。建房、读券、战斗、结算和最后回主界面只维护一份。原 `login`、`all` 仍用奖励入口，不额外执行刷秘境线路。

新入口每次点击前等待3秒并重新截图定位，点击后等待5秒，每个定位阶段最多等待180秒，模型调用上限为10次。未识别成功时按公共规则等1秒补查一次，再回当前轮询；不重复点击上一页入口。先提取白字深色描边的竖排文字候选，将带编号的候选图片发给模型读取文字并选择入口，代码将编号映射回本次截图中的位置。候选提取不使用文字模板；只有模型确认名称且返回有效候选编号才点击。这样避免模型直接报告坐标时出现比例或像素单位混淆。

`login` 和 `all` 的队列在丰饶之间后追加 `secret_realm`，也可用 `run secret_realm --config config.local.json` 单独运行。奖励入口查找秘境卡片时，每次从 `(1450, 550)` 左滑到 `(800, 550)`，等待2秒，最多滑10次，避免长距离滑动跨过边缘卡片。通过奖励任务卡片进入秘境后，识别“创建房间”并点击，模型只读取房间左下角“剩余挑战券”的总数。读到正数时等待后重新截图复核，再点击同一帧识别到的“出战”；读到0结束，队列下一步调用通用回主界面。读取失败不当作0，出战后不因网络延迟重复点击。

秘境点击前等待3秒，创建房间、进入活动和战后刷新等待5秒，出战后等待15秒再调用战斗模块；不再等待暂停按钮识别，战斗最多300秒。模型使用已有 `.env` 配置，每轮读券阶段最多6次调用。每次回房间后重新读取当前券数，出战前复查大于0就继续挑战，为0则结束；不比较战前战后的券数，也不等待扣券。券数无法识别时仍补查，不能把未知当成0或直接出战。

战斗结束标记包含“恭喜你获得”奖励弹层、秘境结算页的翻牌说明及房间“出战”按钮。识别到奖励弹层便停止攻击，点击下方空白处 `(960, 900)`，逐轮检查直到回房间，无需先找到左下角返回。奖励弹层和翻牌结算的返回状态分别记录，兼容它们先后出现的情况。发现结算页后先停止攻击，同一张截图中同时确认结算说明和左下角“返回”，等待3秒复查后点击返回，等待5秒刷新。等待期间若已自动回到房间，不再点击返回；点击返回后循环检查房间，尚未返回就点击屏幕下方空白处 `(960, 900)` 关闭通关过渡页，并按轮询间隔等待后再检查。确认回到房间后立即停止点击并重新读取挑战券；若返回大厅则重新创建房间。超过结算等待上限仍未返回则报错停止，不继续出战。

兼容旧配置：`battle_marker` 和 `start_timeout_seconds` 字段暂时保留，但通用战斗模块不再使用它们进行入场识别或等待。


秘境出战加载后，先用现有大模型读取顶部副本名称。确认是“阴阳秘境”时，调用 `exit_secret_battle()`，依次识别并点击右上角暂停、“退出战斗”、退出确认框内的“确定”。每一步点击前重新截图复查；“确定”必须与“确认退出本次战斗吗”提示出现在同一帧。确认是“毒风秘境”时，先由场景模块通过代码调用导航 agent，传入走到封印处的目标，逐步移动；模型明确确认到达后才执行通用战斗，50 步耗尽则调用同一个退出函数。其余已识别秘境使用通用快速战斗；名称未知则重新截图重试，超过调用或等待上限报错停止。

阴阳秘境或毒风导航耗尽后退出，均沿用返回房间流程，重新读取挑战券并继续刷。主动退出和战斗结束都只根据当前券数决定是否继续，不要求券数下降。日志中的战斗场数统计已结束的战斗，不作为通关判断，主动退出不计入该数量。副本名称识别只在每次秘境出战后运行；毒风导航每步重新截图调用模型，不影响丰饶之间，也不会在每轮技能点击时调用模型。

验证范围：用户提供的副本名称截图已通过真实模型识别；按钮模板和退出流程经过截图回放测试。毒风导航已通过秘境 handler 和 agent 的离线集成测试，覆盖到达后战斗、50 步耗尽退出和异常停止；摇杆位置按 1920×1080 战斗参考截图设置。回放中的页面切换由测试模拟，尚未完成毒风导航或阴阳退出的整段实机验证。
